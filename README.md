# Лабораторная работа №3: Автоматизированная работа с хранилищами данных с использованием фреймворка dbt (data build tool)

## 1. Цель работы

Целью данной работы является изучение принципов автоматизации процессов трансформации данных (ELT) внутри хранилища с использованием фреймворка dbt (data build tool). В качестве целевой СУБД для реализации проекта автоматизации аналитики службы каршеринга было выбрано современное встраиваемое хранилище данных DuckDB. 

Процесс развертывания включал следующие этапы:
1. Активация виртуального окружения Python и установка адаптера командой `pip install dbt-duckdb`.
2. Инициализация dbt-проекта командой `dbt init my_carsharing_dbt`, в ходе которой была сгенерирована базовая структура папок для моделей, тестов и конфигураций.
3. Настройка профиля подключения в файле `profiles.yml` для корректной работы с локальным файлом базы данных `dev.duckdb`.

## 3. Разработка скриптов автоматизированной работы (модели)

В соответствии с предметной областью «Служба каршеринга», аналитическая система оперирует данными об автомобилях, зонах парковки, пользователях, поездках, тарифах (по времени/пробегу) и текущем состоянии авто. В папке `models/` были разработаны SQL-скрипты, реализующие логику трансформации этих данных:

* **Модель Staging (`stg_trips.sql`)**: Выполняет первичную обработку, очистку и профилирование «сырых» исторических данных о поездках пользователей. Включает в себя фильтрацию аномальных записей (например, поездок с нулевым временем или отрицательным пробегом), приведение типов данных для временных меток (типы данных для тарификации по времени) и идентификаторов, а также нормализацию текстовых полей.
* **Модель Marts (`car_performance.sql`)**: Формирует итоговую многомерную аналитическую витрину, оценивающую производительность и износ автопарка. Используя макрос `{{ ref() }}` для связывания очищенных данных о поездках (`stg_trips`) с сопутствующими сущностями (техническое состояние авто, тарифные сетки за пробег/время и зоны парковки), скрипт рассчитывает ключевые бизнес-метрики (KPI) для каждого автомобиля: суммарный пробег, совокупную коммерческую загрузку в часах, общую принесенную выручку и частоту фиксации критических состояний машины.

## 4. Развертывание и проверка

Запуск комплексного процесса трансформации, компиляция SQL-кода и создание физических таблиц/представлений в базе данных DuckDB произведены в консоли с помощью команды: `dbt run`. Валидация рассчитанных данных в созданной витрине производилась через Python-интерфейс DuckDB, что подтвердило полную корректность расчетов агрегатов, правильность применения формул тарификации и связности данных.

## 5. Постановка работы скриптов на расписание

Для обеспечения регулярного обновления аналитики и поддержания актуальности данных по поездкам и состояниям автомобилей была настроена автоматизация запуска dbt без привлечения тяжеловесных внешних оркестраторов. 

С помощью системного планировщика Cron в операционной системе Linux (WSL) была настроена регламентная задача на ежечасный запуск процесса сборки витрин. Проверка статуса планировщика через команду `crontab -l` подтвердила успешную регистрацию и запуск задачи:
`0 * * * * cd ~/airflow_lab/my_carsharing_dbt && ~/airflow_lab/airflow_env/bin/dbt run`

## 6. Вывод

В ходе лабораторной работы был успешно развернут фреймворк dbt и реализован законченный цикл ELT-процесса для службы каршеринга. На примере интеграции данных о пользователях, тарифах, автомобилях и их поездках продемонстрирована отказоустойчивая автоматизация создания аналитических витрин, способных обновляться автономно по заданному cron-расписанию. Использование dbt позволило изолировать и инкапсулировать логику трансформации от непосредственного слоя хранения данных, что соответствует современным стандартам проектирования систем Big Data.
